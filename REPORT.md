# Отчёт: GrapheneOS 2026100601 + KSU Next 3.4.1

Обновлено 2026-10-13. Pixel 8 shiba, Android17, SPL2026-10-05. История предыдущего выпуска: [archive/2026100201/REPORT.md](archive/2026100201/REPORT.md). Это экспериментальная интеграция, не официальный продукт GrapheneOS.

## Итог, подтверждённый измерениями

На двух Pixel 8 выполнены временные тесты, затем по явному разрешению владельца записан **только boot_a**. После постоянной загрузки: GrapheneOS2026100601, slot_a, boot_completed1, bootreason=reboot, kernel6.1.177-android14-11-g5969734141aa, 316 модулей, SELinux Enforcing. Packaged ksud через UID Manager показывает Kernel Version33333 и debug su → uid0/gid0, u:r:ksu:s0. На первом телефоне также работает adb shell su; на чистом втором shell root отдельно не разрешался.

Manager исправлен, включает arm64 libksud.so с PRCTL-транспортом. На обоих устройствах Manager завершил установку служебных файлов с `install result: true`. Заключительная проверка первого телефона выполнена после обновления исправленного APK и повторной записи boot_a.

Neo Backup/Termius после новой установки отдельно не проверялись. Нельзя переносить старый положительный результат 3.4.0 на новую версию. Результаты APK LKM installer также не заявляются: здесь встроенный KSU.

## Исправление ошибочных утверждений о ранних тестах

Ранние утверждения, что первые кандидаты341 успешно загрузили Android и штатные модули, **отозваны**. Последующая диагностика показала:

1. В ядро ошибочно перенесли публичный module cert от2026100201 (DER fingerprint7cb124fd02556bc62e493db700e7a5ad4003696e0abefcd74c2b149407ff72c2).
2. В LAST KMSG были успешная ранняя инициализация KSU, затем `Loading of module with unavailable key is rejected` / `Key was rejected by service` для exynos-pd, vh_fs, vh_thermal, USB и UFS модулей.
3. Boot reason сообщил APC Watchdog Early. Android, доступный затем по ADB, работал уже после возврата на stock.
4. KSU строки были ошибочно взяты из LAST KMSG, а не текущего dmesg. Matching release suffix и sys.boot_completed позволили пропустить возврат на stock.

Поэтому старые тестовые candidates/debug/diag **не распространяются как рабочие**. Изменён только trust PEM, MODULE_SIG_FORCE сохранён. С новым matching cert временный boot действительно дал FD и работающий root, затем образ установлен.

`prctl` может вернуть EINVAL (-1/errno22) даже при успешной установке FD через task_work: неизвестная Linux prctl operation возвращает ошибку, а KSU отдельно записывает fd. Поэтому оценивать только syscall return без fd/ioctl неверно.

## Ошибка комплектации Manager

Первый341 APK содержал JNI libkernelsu.so, но не libksud.so. Gradle успешно собрал неполный APK. На первом телефоне старые компоненты и ранее выданные права маскировали ошибку; Manager shell chain `libksud.so debug su || su || sh` мог использовать существующий su.

Чистый второй телефон выявил отказ root. Текущий dmesg доказал signer match, `Crowning manager` и FD выдачу. Проверка ZIP обнаружила отсутствие executable. Собран patched ksud (Rust, NDK29/API35, cargo --locked), добавлен в jniLibs, APK пересобран Java21 с тем же signer. После обновления Manager install result true, независимый run-as Manager → packaged ksud debug su вернул uid0 в Enforcing. Добавлен preBuild guard на отсутствие arm64 ksud.

## Состав исходных изменений

Пять патчей для новой базы сохранены отдельно. MTE-патч удаляет дополнительные untagged_addr transformations в KSU user-pointer reads. PRCTL-патч меняет kernel/ksud/ksuinit/susfsd/JNI. ACK включает KSU и matching module cert. Kleaf host overrides задают version/package/signer и release suffix. Исходники KSU и uapi копировались в drivers/kernelsu: symlink integration первоначально не прошла sandbox.

Патчи содержат диагностические pr_info из фактически проверенной сборки. Фильтр UID10243 — диагностика первого телефона, не правило авторизации; UID второго отличается. Избыточное логирование можно удалить отдельным будущим изменением с новым тестом. Менять и молча называть новый образ тем же проверенным нельзя.

## Уроки и границы публикации

Каждый результат привязан к точному APK/kernel hash и конкретной загрузке. Сначала журналы и гипотеза, затем целевая правка; тестировать как существующую установку, так и чистое устройство. Не отключать MTE/SELinux/module signatures ради обхода ошибок. Проверки driver transport, manager identity, root Manager, shell authorization и приложений независимы.

Полные bugreport содержат личные данные; они и private APK keys не публикуются. Здесь сохранены только технический итог и воспроизводимые команды. Старые личные логи и локальные build caches не являются частью выпуска.
