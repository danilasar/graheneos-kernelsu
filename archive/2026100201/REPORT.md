# Отчёт: экспериментальная интеграция KernelSU Next на Pixel 8 / GrapheneOS

**Обновлено:** 2026-10-07
**Устройство:** Google Pixel 8 (`shiba`)
**Проверенная система:** GrapheneOS `2026100201`, Android 17
**Архив документов и файлов выпуска:** `ksu-next-shiba-2026100201-release/`

> Это хронологический отчёт; ранние разделы описывают неудачные промежуточные состояния. Их заменяют итоговые разделы 17–23 и отдельные инструкции `INSTALL.md` и `UPDATE.md`. Исходные репозитории ядра и временные журналы сборки и отчёты об ошибках впоследствии удалены по запросу пользователя; сохранены отчёт, инструкции, набор патчей и файлы выпуска.

## Итоговое состояние

- KernelSU Next v3.4.0 встроен в образ ядра (`CONFIG_KSU=y`). Исправление чтения пользовательских указателей вернуло перехват запуска zygote и поиск менеджера, а транспорт через `prctl` обходит запрет `reboot(2)`, который в GrapheneOS накладывает seccomp.
- Проверенный образ размером 64 МиБ со свойством AVB «уровень исправлений безопасности» `2026-09-05` записан **только в `boot_b`**. `init_boot_b` ранее менялся отдельным экспериментом; последние установки его не трогали. `vendor_kernel_boot`, `vendor_dlkm`, `system_dlkm`, `dtbo` и `vbmeta` на заключительном этапе не прошивались.
- Телефон загрузился со слота `_b`; проверка `adb shell su -c id` вернула UID 0 в контексте `u:r:ksu:s0`. Root в Termius и в ADB работает через `su`; `adb root` — отдельная функция, и она не означает root для `adbd` выпускной сборки.
- Neo Backup (`com.machiav3lli.backup`) заработал после добавления привилегий (capabilities) в его отдельный профиль KernelSU. На текущем телефоне в профиле включены все привилегии данной сборки; минимальный набор не выяснен.
- Итоговый образ проверен на сборке GrapheneOS `2026100201` (`CP3A.260905.009`). Не использовать на другой сборке без пересборки и проверки.
- На заключительном этапе `fastboot -w` не запускался. Разблокировка загрузчика и первые эксперименты описаны в истории, но нынешние инструкции по установке и обновлению рассчитаны на работу без потери данных, кроме неизбежного стирания при разблокировке загрузчика.

В рабочем дереве остались экспериментальные изменения:

- `build/kernel/_setup_env.sh` — в песочницу Bazel явно передаются версия и тег KernelSU Next, поскольку в песочнице нет вложенных метаданных `.git`:

- `build/kernel/kleaf/impl/stamp.bzl` — версия из системы контроля версий жёстко задана как `-gf6f62ba75ac9`, чтобы итоговая версия модулей совпала с установленной GrapheneOS. Это локальное экспериментальное переопределение, а не универсальное изменение Kleaf.

## 5. Подготовка и проверка `boot.img` с KSU

Первый локальный `out/shusky/dist/boot.img` имел размер 53 477 376 байт (51 МиБ), тогда как физический раздел `boot_b` — 67 108 864 байта (64 МиБ). В его хвостовом блоке AVB было только разработческое значение уровня исправлений безопасности `2027-03-05`; это значение задаёт сборочный скрипт GKI для экспериментальных образов на разблокированных устройствах.

Сначала этот образ использовался **только** для временной загрузки:

```bash
fastboot boot android-kernel-build/kernel_pixel_6.1/out/shusky/dist/boot.img
```

Затем из него извлекли ядро, собрали образ с загрузочным заголовком версии 4 и создали кандидат правильного размера с хвостовым блоком AVB под раздел 64 МиБ. Итоговый файл:

```text
android-kernel-build/ksu-next-3.4.0-2026100201-boot-64m-candidate/boot.img
размер: 67 108 864 байта
SHA-256: 35b5ba30fa998b96d0027e2f67cc73e7913f690a34e484b843ee2ebd3eb1085e
```

Ключевые команды упаковки:

```bash
python3 tools/mkbootimg/mkbootimg.py \
  --header_version 4 \
  --kernel /tmp/current-boot-unpack/kernel \
  --ramdisk /tmp/current-boot-unpack/ramdisk \
  --cmdline '' \
  --output /tmp/boot.raw.img

prebuilts/kernel-build-tools/linux-x86/bin/avbtool add_hash_footer \
  --image /tmp/boot.raw.img \
  --partition_name boot \
  --partition_size 0x4000000 \
  --prop com.android.build.boot.security_patch:2027-03-05
```

`avbtool verify_image` подтвердил целостность хвостового блока и хеша локального образа. Ядро, извлечённое из кандидата, совпало с ядром из временно загруженного образа.

Кандидат сначала загрузили без записи в раздел:

```bash
adb reboot bootloader
fastboot getvar current-slot
fastboot getvar unlocked
fastboot boot android-kernel-build/ksu-next-3.4.0-2026100201-boot-64m-candidate/boot.img
```

Android загрузился; остался слот B, загрузились 316 модулей, включая `bcmdhd4398`, `gxp`, `mali_kbase`, `gs_thermal`. Затем обычная перезагрузка вернула устройство на штатный загрузочный раздел.

## 7. Проверка KernelSU и причина отказа

После прошивки ядра система загружается, но менеджер сообщает, что KernelSU не установлен. Был запрошен и извлечён отчёт об ошибке:

```text
android-kernel-build/KernelSU_Next_bugreport_2026-10-05_17_19.tar.gz
```

Извлечённые файлы:

```text
android-kernel-build/ksu-bugreport-2026-10-05-17-19/
```

`kernel_status.txt`:

```text
no_driver: kernel has no KernelSU-Next hook
manager_appid: 0
```

`basic.txt` содержит `KernelSU: -1`, менеджер v3.4.0 (33294), `LKM: false`. В `logcat.txt` многократно повторяется:

```text
KernelSU driver install syscall was blocked by seccomp
could not retrieve kernelsu driver fd
```

Причина подтверждается исходниками KernelSU Next:

- `userspace/ksud/src/ksucalls.rs` вызывает `libc::SYS_reboot` с «магическими» значениями KSU, чтобы получить файловый дескриптор драйвера.
- `kernel/supercall/supercall.c` перехватывает этот вызов в `reboot_handler_pre()` и выдаёт дескриптор.
- На GrapheneOS seccomp блокирует `reboot(2)` в процессе менеджера (`untrusted_app_34`) раньше, чем системный вызов доходит до точки перехвата (kprobe) в ядре.

Поэтому наличие `CONFIG_KSU=y`, успешная загрузка ядра и загрузка штатных модулей сами по себе не доказывают, что KSU работает на запущенной системе. В данном случае дескриптор драйвера не получен, `manager_appid=0`, root через KSU не работает. Дополнительное изменение `init_boot` эту проблему не устранило.

**Исправление требует либо** изменить и пересобрать обе стороны протокола — KernelSU в ядре и `ksud` с APK менеджера — под системный вызов, который seccomp в GrapheneOS разрешает, **либо** менять политику seccomp самой ОС. Простая настройка приложения или ещё одна прошивка `boot`/`init_boot` проблему не устраняет. Глобально разрешать `reboot(2)` всем приложениям небезопасно.

## 11. Дополнение: экспериментальный перевод супервызова на `prctl` (2026-10-05)

После выяснения причины, связанной с seccomp, была проверена политика GrapheneOS для Android 17 в `GrapheneOS/platform_bionic`, ветка `17`: `reboot` входит в `libc/SECCOMP_BLOCKLIST_APP.TXT`, тогда как `prctl` указан в `libc/SYSCALLS.TXT` и в списке запрещённых для приложений отсутствует. Поэтому новым транспортом для супервызова KSU (supercall) выбран `prctl(2)`; пока это гипотеза, которую ещё нужно подтвердить на самом процессе приложения.

Локально изменены исходники KernelSU Next:

- добавлена точка перехвата (kprobe) на `__arm64_sys_prctl` (и `__x64_sys_prctl` для x86_64), использующая обработчик супервызова; старая точка перехвата на `reboot` оставлена для совместимости;
- запросы дескриптора драйвера KSU в `userspace/ksud/src/ksucalls.rs` и `userspace/ksuinit/src/lib.rs` переведены с `SYS_reboot` на `SYS_prctl` с пятым аргументом `0`;
- вызовы в `userspace/ksud/src/susfsd.rs` также переведены на `SYS_prctl`.

## 12. Анализ журналов и дополнительная правка менеджера (2026-10-05)

Получены файлы из `Download`:

Исходная проверка `ksud debug version` доказывала только, что `ksud` на Rust через `prctl` получает дескриптор и читает версию; для интерфейса менеджера этого было недостаточно. C++ JNI probe

### 18. Проверка ADB/Termius и NeoBackup (дополнение)

Проверка root из ADB выполнялась командой:

```sh
adb -s 38221FDJH006CS shell su -c 'id; id -u'
```

В ранней попытке `/system/bin/su` отсутствовал, а обычная оболочка ADB работала с UID 2000. Это не означало отсутствия root: KernelSU перехватывает обращение к `su` для разрешённого UID (`sucompat`), а физический файл `/system/bin/su` не обязателен. Позже проверка через `adb shell su -c ...` успешно дала `uid=0`, контекст `u:r:ksu:s0`; Termius (`uid=10201`) также проходил через `sucompat`. Отдельный запрос `adb root` в одном из ранних состояний отвечал `adbd cannot run as root in production builds`; это относится к режиму root самого `adbd`, а не к `su` в оболочке ADB. Эти две проверки не равнозначны.

Для NeoBackup (`com.machiav3lli.backup`, UID 10193) журнал ядра показал сохранённое разрешение `allow: 1`. Отчёт об ошибке `neo-backup-selinux-test/bugreport.zip` содержит попытки `sys_execve su found` и выдачу дескриптора KSU; журналы самого NeoBackup сообщали `libsu uses root shell = true`. Его проверка, однако, завершалась с кодом `127`:

```text
sh '/data/user/0/com.machiav3lli.backup/files/assets/plugin/checkroot.internal_sh'
Permission denied
is NOT like root
```

В том же отчёте об ошибке SELinux вернули в принудительный режим (Enforcing) в `14:07:58`; ошибка скрипта случилась около `14:08:16`, а переключение в разрешающий режим (permissive) произошло только в `14:08:29`. То есть именно эта неудачная проверка пришлась на принудительный режим, несмотря на последующую проверку в разрешающем.

**Итоговый результат у пользователя:** NeoBackup заработал после добавления ему необходимых привилегий в профиле KernelSU. Точные названия добавленных привилегий в истории не указаны. Termius и ADB, по сообщению пользователя, также работают.

В ответ на просьбу «исправляем и прошиваем» локально добавлялся запасной вызов `untagged_addr()` только в коде ADB Root, и полная сборка прошла. После уточнения, что Termius и ADB уже работают, это локальное изменение исходников было отменено. Сборка и её результаты остались только на компьютере: **этот образ с запасным вызовом не загружался и не прошивался**. Никаких новых записей в разделы после временной проверки исправления MTE не было; активным слотом оставался `_b`.

Основные команды из сессии:

```sh
# Сборка shusky
KLEAF_REPO_MANIFEST=aosp_manifest.xml ./build_shusky.sh --lto=full

# Проверка su через ADB
adb -s 38221FDJH006CS shell su -c 'id; id -u'

# Проверка root-режима adbd (отдельно от su)
```

### 23. Состояние после GrapheneOS OTA

При последующей read-only проверке телефона ADB показал build `2026100601`, fingerprint `google/shiba/shiba:17/CP3A.261005.005/2026100601:user/release-keys`, активный слот `_a` и kernel `6.1.177-android14-11-g5969734141aa`. Обычная ADB shell оставалась UID 2000; `su -c id` завершился `su: inaccessible or not found`. Пакеты `com.rifsxd.ksunext.prctl` и Neo Backup остались установлены. Это соответствует обновлению GrapheneOS на новый слот со штатным ядром; наличие APK Manager не означает наличие активного KSU-драйвера. Артефакты этого комплекта относятся к `2026100201` и не должны прошиваться на текущий `2026100601`. Для возврата KSU нужна новая сборка и matching stock/rollback images под `2026100601`.
